Controller grid picker

Requirements proposal · October 6, 2026. This describes a new rtplot control; it is not an implemented API or a trained controller bank.

One grid, three method views. Changing the method keeps the same X–Y position.

Interaction preview

UI demonstration only. J1–J3 and W1–W3 are ordered levels; numerical weights are not frozen.

X: jerk weight increases → · Y: anti-shake weight increases ↑

The real dashboard highlights an active controller only after the Pi accepts the selection. This preview accepts immediately.

1. Experiment and count

  • 27 candidates: three methods × three strictly positive jerk weights × three positive anti-shake weights.
  • Three references: fit + jerk + the same trained 5 Hz filter, one at each jerk weight; anti-shake weight zero. Total: 30 distinct checkpoints.
  • Hardware observation motivating this proposal: the operator reports jerk-free controllers are too noisy. Exclude jerk-free models from this next hardware bank. This is an initial report, not a quantified result for every model.
  • Freeze numerical levels before training. Reuse compatible completed runs rather than training duplicates. Match data split, fitting target, mass/gain conditioning, filter, epochs and seed. Freeze probe band, probe inputs and loss calibration; disclose any differences between methods.
  • Axes select immutable checkpoints. These are training loss weights, not live assistance gain or editable model coefficients.

2. Required selection behavior

  1. One 3 × 3 grid and one method dropdown for magnitude, damping and positive energy. Equal-sized cells; explicit row/column labels with exact values. Rows increase from bottom to top; jerk increases left to right.
  2. Preserve X and Y when the method changes. Use the same three jerk values and the same three calibrated-multiplier values across the methods; keep the displayed axis values unchanged. Each method can have its own fixed calibration, so its absolute coefficient may differ. If M at (J2,W3) is selected, choosing D requests D at (J2,W3). Resolve the new checkpoint even though the coordinates did not change. Do not fall back to the first cell or the nearest available weight.
  3. Selection is discrete. Click/tap or keyboard activation requests one declared cell. No interpolation, drag-to-switch or requests on hover/focus. Do not silently equate a calibrated multiplier with another method’s absolute coefficient.
  4. Matched reference: “Reference at this jerk” selects the reference corresponding to the current jerk column. Remember the anti-shake row. Clicking the grid or selecting a method returns to that method at the remembered/current coordinates. Show “Reference · J2” as active; do not falsely mark an anti-shake checkpoint active.
  5. Application acknowledgment: distinguish chosen coordinates/requested model from the confirmed active controller. Show pending/loading and rejection reasons. A rejected request leaves the prior active model and confirmed coordinates/method intact.
  6. Unavailable cells: disabled with a reason, such as “Not exported.” Reject method changes whose corresponding checkpoint is unavailable. Keep the prior model and X–Y position; never substitute another checkpoint.
  7. Global active state: exactly one active controller, including references. Mirror authoritative state across viewers and reconnects. Preserve X–Y on method changes, presentation changes and reconnects to the same layout. A new source/layout starts from application-declared defaults.
  8. Changing views must not rebuild plots or reset telemetry history. Coordinate IDs remain stable when labels or cell contents change.

3. Proposed generic rtplot interface

Keep the widget generic: rtplot displays a discrete coordinate pair; the application maps (method, x_id, y_id) to a controller ID. The method dropdown remains an ordinary dropdown. Wire/API names below are proposed, not existing capabilities.

{
  "type": "grid_picker",
  "id": "controller_weights",
  "label": "Training weights",
  "x_label": "Jerk weight",
  "y_label": "Anti-shake weight multiplier",
  "x_options": [
    {"value": "j1", "label": "J1: <exact weight>"},
    {"value": "j2", "label": "J2: <exact weight>"},
    {"value": "j3", "label": "J3: <exact weight>"}
  ],
  "y_options": [
    {"value": "w1", "label": "W1: <exact multiplier>"},
    {"value": "w2", "label": "W2: <exact multiplier>"},
    {"value": "w3", "label": "W3: <exact multiplier>"}
  ],
  "value": {"x": "j2", "y": "w2"}
}
  • Provide dictionary and typed declarations, validation, and a new advertised capability such as grid_picker_v1. A generic grid supports arbitrary finite axes, not just 3 × 3. Stable option IDs must be unique per axis; defaults must identify declared coordinates.
  • Expose a discrete request containing control ID, X/Y IDs and request ID through an additive channel, e.g. ControlState.grid_requests. Preserve existing values and buttons behavior. Initialization and presentation changes emit no requests. Drain requests once per poll; the application deduplicates request IDs and rejects stale layout/source generations.
  • Allow application-confirmed selection updates, e.g. set_grid_picker(id, x, y), without producing input events. Atomically update grid, method and active-model readout so viewers do not see contradictory accepted states.
  • Support control-wide enabled/visible/busy/reason and per-cell enabled/busy/reason overrides. Busy alone does not disable a control. Update cell labels/availability and accepted coordinates without full layout initialization.
  • A method change resolves using the last confirmed coordinate pair. If method and coordinate requests arrive together, resolve one explicit final pair and apply at most one controller switch; never briefly load an intermediate combination. Handle requests sequentially and keep accepted versus pending state distinct.
  • For an unsupported server, the application explicitly falls back to the existing flat controller dropdown with full labels. Do not present a grid whose disabled/selection semantics are unenforced.

4. Pi dashboard integration

  • Put the method dropdown, grid, matched-reference button and compact active-model readout in the main controller section. Keep Stop torque in its persistent position; diagnostics and logging remain collapsed.
  • For this experiment, accept switches with torque OFF. A successful switch resets controller/filter histories, shows warmup, and requires separate enable. Never infer hardware success from a browser click. The app enforces this policy; rtplot remains a generic UI transport.
  • Show method, jerk coefficient, anti-shake multiplier, actual calibrated coefficient, controller ID and readiness for the selected checkpoint. Keep body mass and assistance gain as distinct live controls.
  • Map cells through the export manifest, not filenames or arithmetic on row indexes. Available means exported, hash-verified and loadable. Keep epoch, seed, probe band/inputs, jerk definition and filter settings in model metadata.
  • Log accepted switches with controller ID/checkpoint hash, method, grid coordinates, coefficients, mass/gain, command settings and timestamp. UI view changes alone do not count as accepted switches. Retain raw hardware logs.
